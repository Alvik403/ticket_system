# Архитектура MVP

## Поток

1. Статический QR ведёт на `/client` и передаёт только публичный код площадки
   (`?site=MAIN`). QR не создаёт walk-in талон и не открывает выбор площадки
   или услуги: клиент молча попадает на единственную площадку.
2. Клиент выбирает дату со следующего рабочего дня и слот. API ставит Redis
   hold на конкретный стол на 3 минуты, затем принимает ФИО, поездки и согласие.
3. Создание записи атомарно: `pg_advisory_xact_lock` по площадке, проверка
   занятости, потребление hold и вставка `BOOKED`. Частичный уникальный индекс
   запрещает два активных талона на один стол и время.
4. До явки талон не попадает диспетчеру. Кнопка «Я на месте» доступна за 15
   минут до слота и до его окончания. Check-in переводит запись в `CHECKED_IN`
   (`priority = 1`) и в той же транзакции пытается назначить свободного
   сотрудника.
5. Живая очередь — явившиеся (`CHECKED_IN`, `REQUEUED`), сортировка: свой стол,
   затем `priority DESC`, затем `scheduledAt`. Пауза сотрудника и `REQUEUE`
   возвращают талон в `REQUEUED` с `priority = 0`.
6. Сотрудник вызывает, начинает и завершает обслуживание. Команды принимают
   `Idempotency-Key` (ответ кэшируется в Redis на 24 часа). После `COMPLETE`
   диспетчер назначает следующего явившегося в той же транзакции. Редкий sweep
   (около 12 с) только страхует свободных сотрудников.

## Состояния

Талон: `BOOKED → CHECKED_IN → ASSIGNED → CALLED → IN_SERVICE → COMPLETED`.
Из `BOOKED`, `CHECKED_IN`, `ASSIGNED`, `CALLED` или `REQUEUED` возможна отмена.
`NO_SHOW` — после вызова или вручную сотрудником/админом для `BOOKED` после
окна явки. Автоматического `NO_SHOW` нет. Переназначение и пауза сотрудника
возвращают талон в `REQUEUED`.

Сотрудник: `OFFLINE | AVAILABLE | RESERVED | BUSY | PAUSED`.
`RESERVED` и `BUSY` устанавливаются сервером, остальные состояния выбирает
сотрудник при отсутствии активного назначения.

## Граница доверия

`/api/public/*` не использует учётную запись. Привязка клиента — серверная
cookie-сессия с хешем секрета талона; сырой секрет в JSON и Redis не
возвращается. Восстановление записи — номер + короткий код (хранится как
хеш). `/api/employee/*` требует сессию и роль `EMPLOYEE` либо `ADMIN`.
`/api/admin/*` требует `ADMIN`. `/api/auditor/*` — `AUDITOR` или `ADMIN`,
без ФИО клиентов. Живая очередь сотрудника показывает номер, слот и стол,
без ФИО. Полное ФИО — только у своего активного назначения.

OIDC Authorization Code + PKCE выполняется сервером. Роли берутся из
проверенных claims и UserInfo, без декодирования JWT без подписи. Браузер
получает только идентификатор серверной сессии; OIDC-токены не помещаются в
`localStorage`. Сессии находятся в Redis, а состояние очереди и события — в
PostgreSQL. Слоты считаются в `site.timezone` (`Europe/Moscow`).

## Отказоустойчивость

Redis можно восстановить без потери очереди; сотрудники войдут повторно,
неистекшие hold и idempotency-ответы пропадут. PostgreSQL — единственный
источник истины и должен иметь point-in-time recovery. При потере связи
интерфейс перечитывает текущее состояние с API.
