# Эксплуатация и восстановление

## Наблюдаемость

Контролировать: HTTP 5xx и p95, ошибки OIDC, число ожидающих талонов, возраст
старейшего талона, зависшие `ASSIGNED/CALLED/IN_SERVICE`, ошибки диспетчера,
PostgreSQL connections/replication lag, Redis memory и срок последнего backup.
Application logs не должны содержать секрет талона, cookie, OIDC token или
полный IP клиента. Просроченные талоны и записи аудита удаляет
`RetentionService` по `RETENTION_TICKET_DAYS` и `RETENTION_AUDIT_DAYS`.

## Резервирование

- PostgreSQL: ежедневный full backup и WAL/PITR; backup шифруется и остаётся в РФ.
- Redis: не считается резервной копией очереди; потеря приводит к повторному
  входу сотрудников, но не к потере талонов.
- Конфигурация Keycloak экспортируется отдельно без секретов; учётные записи и
  MFA восстанавливаются по процедуре IdP.
- Не реже раза в квартал разворачивать backup в изолированной среде и
  документировать фактические RPO/RTO.

## Сбой

1. Остановить входящий трафик изменения состояния, сохранив read-only статус.
2. Зафиксировать время, алерты, версии и ответственных; не удалять журналы.
3. При сбое Redis перезапустить его и попросить сотрудников войти снова.
4. При сбое PostgreSQL переключиться на согласованную replica либо выполнить
   PITR. До открытия трафика проверить уникальность активных назначений.
5. Сверить `Ticket.status` с последним `TicketEvent`; исправления проводить
   контролируемой миграцией с отдельным `AuditEvent`, а не ручным UPDATE.
6. После восстановления пройти сценарий талон → назначение → завершение.
7. При признаках неправомерного доступа включить утверждённый процесс
   реагирования и регуляторных уведомлений.

## Проверка нагрузки

После установки k6:

```text
k6 run test/load/queue.k6.js
```

Профиль по умолчанию проверяет 100 виртуальных пользователей, менее 1% ошибок и
p95 публичного каталога менее 500 мс. Перед пилотом заменить профиль на
ожидаемый пик площадки с трёхкратным запасом.
